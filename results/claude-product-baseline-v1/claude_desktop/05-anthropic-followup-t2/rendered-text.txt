The structure to follow
Weave uses four nested concepts, and they map neatly onto a hand-written loop. A conversation groups turns; a turn is one user message and the agent’s complete response (an 
invoke_agent
 span); an LLM call is one call to a model API (a 
chat
 span); and a tool call is one tool execution triggered by an LLM response (an 
execute_tool
 span). In Python, all four functions work as context managers (
with weave.start_*(...) as obj:
), and on exit they end the span and flush attributes, including on exceptions.

start_llm

start_tool

Anthropic-specific details that matter
There are a few things to get right when calling Anthropic. Set the provider yourself: pass 
provider_name
 explicitly, because Weave doesn’t infer it from the model string. Token accounting is the most common mistake. Anthropic reports cached tokens separately from 
input_tokens
, so you need to add them back into the total Weave prices against. This matters because for providers with prompt caching, cached tokens routinely dominate the input, so omitting them makes usage and cost render as roughly zero. Always pass 
response_model=resp.model
, since an alias is not priceable and renders 
Cost -
, so you should pass the concrete id the response returns. Finally, Weave’s 
arguments
 expects a JSON string, so 
json.dumps(block.input)
. 
Where tool spans go
You have a choice about where tool spans attach. A tool span becomes a child of whatever OTel span is active in context, typically the 
chat
 span of the LLM call that produced the tool call. The reference example runs tools inside the 
start_llm
 block, which nests them under the call that requested them. The quickstart runs them after the block, as siblings under the turn. My example uses the sibling layout, which keeps each 
chat
 span’s latency limited to the model call. If you’d rather see causality in the tree, move the tool loop inside the 
with weave.start_llm(...)
 block. 
coreweave
Conversations across requests
If your app is a server handling one turn per request, don’t keep a conversation open in memory. If you pass a 
conversation_id
, it must be stable across the lifetime of the conversation, and you reuse the same ID to add new turns to an existing conversation. So per request you’d do 
with weave.start_conversation(agent_name="my-agent", conversation_id=session_id): run_turn(...)
. This works well because each turn starts its own OTel trace, with turns grouped by a shared 
conversation_id
 rather than a parent span. 
coreweave
coreweave
Smaller conveniences
You don’t need to thread span objects through your code. Any function called within a block can call 
start_llm()
 or 
start_tool()
 without holding an explicit reference to the parent, and this works across module boundaries as long as the code runs in the same async context. Your tool-dispatch code can therefore open its own 
start_tool
 span. Instrumentation is also safe to leave in production: all agent tracing functions no-op silently when tracing is disabled or the init call is absent. If message content is sensitive, 
start_conversation
 takes 
include_content=False
 to omit message bodies from spans. If you use extended thinking, the reference examples show 
llm.think(...)
 for recording reasoning on the 
chat
 span. 
Once it’s running, traces appear in the Agents tab of your Weave project, where each conversation shows a multi-turn timeline with nested tool calls, token usage, and feedback. The docs also note this workflow is available in CoreWeave Agent Lens, which reads the same trace data, so nothing changes in your code either way.

Here’s an example of why the sum matters. Suppose Anthropic reports 120 uncached input tokens, 9,800 cache-read tokens, and 350 output tokens. You’d pass 
input_tokens=9920
 and 
cache_read_input_tokens=9800
. Weave then charges 9,800 tokens at the cache-read rate and the remaining 120 at the normal input rate. If you passed only 120 as the input, subtracting 9,800 cached tokens from it leaves nothing to price. The docs warn about exactly this: with prompt caching, cached tokens often dominate the input, so leaving them out makes usage and cost show up as roughly zero.

Three details in this code matter for cost:
Use the model id from the response.
 Cost is looked up by model. Weave uses 
response_model
 first and falls back to the 
model
 you passed to 
start_llm
. An alias isn’t priceable, so pass 
resp.model
.
Record before the block closes.
 Set the usage and other response fields while the 
llm
 object is still open, i.e., inside the 
with
 block.
Guard against 
None
.
 The 
or 0

None
. Without it, adding them would raise a 
TypeError
. This is my own defensive addition; the docs’ example adds the fields directly.
record()
 only applies the arguments you actually pass, so you can call it once for usage and again later for messages without overwriting anything.
Two Anthropic-specific notes (from Anthropic’s API, not the Weave docs)
If you stream, Anthropic sends usage in pieces across stream events. The simplest fix is 
client.messages.stream(...)
 and recording from 
stream.get_final_message()
, which has the complete usage. And if you use extended thinking, Anthropic includes thinking tokens in 
output_tokens
 rather than reporting them separately, so I’d leave 
reasoning_tokens
 unset to avoid counting them twice. The Weave docs don’t say how that field is priced.
Input and output messages
If you also meant recording the message content, that’s separate from cost. 
record()
 also accepts 
input_messages

, and the 
Message
 class has helpers like 
Message.user(...)
, 
Message.assistant(text, tool_calls=...)
, and 
Message.tool_result(call_id, output)
. These fill in the chat view but don’t affect pricing.
