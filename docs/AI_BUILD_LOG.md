## Decisions we can explain

- **Direct loop:** the model chooses tools; Python controls execution, evidence, limits and release of the answer. The whole loop is in one module.
- **Local BM25 search:** no vector database or embedding service during a three-hour exercise. This is cheap and inspectable but weaker on conceptual paraphrases. Repeated queries are allowed.
- **Section evidence:** citations identify the actual passage returned by `read_page`, not just a URL that might support the answer. Search snippets are not automatically citeable.
- **Separate verification:** the verifier sees the proposed answer and its evidence. It has no tools or ability to change the source record. Rejected drafts are not stored as conversation answers.
- **Honest limits:** unavailable Docker, provider errors and research exhaustion are visible. A code sample only counts as executed if the recorded container run succeeded.
- **Independent evaluation references:** expected behaviors and source sections are dataset fields available to the judge, not hints sent to the evaluated model.
- **Live monitoring:** a narrow review-needed Signal has a measurable purpose. It does not pretend to replace claim-level checking or human judgment.

The owner requested parallel research on routing/specialists, knowledge graphs, voice and adaptive interfaces, with visible cost and whole-story checks. Three bounded research agents inspected the current code and primary sources. Their findings support selective experiments: domain handoffs can lose shared context; documentation links are a lower-cost starting point than full GraphRAG extraction; audio capture still needs transcription and correction. These are design recommendations, not results from our own comparative trials. The owner also asked to use Weave meaningfully without duplicating its dashboards.

The code review exposed a real accounting gap: `planner_usage` counted planning only, even though Weave already recorded verifier usage. A common model wrapper now counts returned usage from planning, verification and repairs; dated rates produce an estimate, while missing/unsupported usage remains unknown. Independent tests caught malformed-token and cache-lifetime handling errors during this change, which were corrected before the passing suite. We do not label the estimate as an invoice or include unobserved Signal/judge charges.

The local answer library stores actual new UI responses, original context and evidence, usage and trace links. Human review is separate from source verification; nothing is approved automatically. Review history and snapshot differences are retained. The library is excluded from Git and never used as factual retrieval input. The current prompts and retrieval strategy remain the same. Whole-task verification, graph expansion, specialist routing, voice and adaptive response layouts are still proposals in [the research room](../research.html).

### Current evidence

The latest 13-case run gives correctness 4/4 everywhere, but already identifies one failure: [03-tracing-and-signals](../results/submission-v1/cases/03-tracing-and-signals.json) omits the fallibility caveat and receives uncertainty 2/4. The instrument needs more discriminating cases; saying it cannot expose failures is inaccurate. The brief asks for meaningful failure modes, not a particular failure rate.

The quoted standard error of approximately 0.14 is the maximum binomial value at p=0.5 for n=13. At 12/13, the naive plug-in value is approximately 0.074. Neither establishes that two paired runs are equivalent or significantly different. These are selected tasks, not a random population sample. Report paired outcomes and uncertainty; repeated trials, assertions and paraphrases are not independent new tasks. Define pass^3 as the fraction of cases passing all three observed trials, distinct from pass@3 and from cubing a pooled success rate.

### What the research supports

The papers motivate experiments; they do not validate this implementation. [Huang et al.](https://proceedings.iclr.cc/paper_files/paper/2024/hash/8b4add8b0aa8749d80a34ca5d941c355-Abstract-Conference.html) report limitations of correction without external feedback. [Kamoi et al.](https://arxiv.org/abs/2406.01297) distinguish reliable external feedback from fallible prompted feedback. Documentation provides external reference material, but the LLM's interpretation remains fallible. [CoVe](https://aclanthology.org/2024.findings-acl.212/) answers verification questions independently to reduce draft bias; our draft-visible verifier is not an exact reproduction.

[Sub-question coverage research](https://aclanthology.org/2025.naacl-long.301/) motivates checking omissions; its roughly 50% result concerns the systems and tasks studied, not this agent. [Q-CARE](https://arxiv.org/abs/2608.11238) separates query coverage and atomic-claim verifiability. [ALCE](https://arxiv.org/abs/2305.14627) evaluates citation quality separately from correctness; it does not establish that every partially supported material assertion should be released. The acceptance recommendation above is our design judgment.

[Anthropic caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) support combining system and automatic breakpoints. Hits depend on reusable prefixes, minimum length and lifetime; writes cost money. The growing planner history is a plausible fit; the verifier currently serializes changing content into one user payload. [Effort guidance](https://platform.claude.com/docs/en/build-with-claude/effort) describes a quality/cost tradeoff requiring workload evaluation. Measure savings from actual usage, not the presence of a parameter.

### Recommended bounded sequence

1. Freeze assertion/result contracts; calibrate the judge; author and adversarially review realistic cases. Keep the regression suite and reserve unseen cases if tuning continues.
2. Add caching without lowering effort; measure one real multi-step conversation. Fix trial persistence and off-arm scoring before comparison.
3. Add coverage as an experimental verified mode, retaining material-support rules. Test omissions, prior context, partial support and malformed verdicts. Replay identical draft/evidence fixtures to diagnose verifier behavior separately from full-agent changes.
4. Start with six frozen cases, three modes and two trials: 36 case-runs. Validate the instrument, trace links, false rejections, output limits, cost and failure categories. This pilot is not a broad reliability estimate.
5. Decide whether the full 216 case-trials are justified after the pilot. At $0.15 each they are $32.40 for the agent alone; scaling the two observed turns' mean gives approximately $45.47 before judging, regression, extra turns and repairs. These are scenarios, not forecasts or an authorized spending cap. Execution needs a total run budget and stop/resume behavior.
6. Ship a concise README with setup, architecture, honest comparison/failure findings and Weave links. Keep material limitations beside the claims they qualify; put detailed receipts in `results/`. Recheck the app and fresh setup after code changes. Stream progress before verification, then release the checked answer.

No application changes, paid model runs, library deletion or branch moves were performed in this review. The next implementation should use an agreed scope rather than silently adopting a four-to-five-hour expansion of the roughly three-hour brief.
