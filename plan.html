Take-Home Assignment: Agentic Documentation Assistant

Overview
Build an agentic assistant that answers complex questions about the Weave documentation. Unlike a simple RAG chatbot, your agent should be able to reason across multiple doc pages, verify its own answers, and handle multi-step questions — all while being fully traced and evaluated using Weave.

You are expected and encouraged to use AI coding tools (Cursor, Claude Code, Codex, etc.) to build this project. How you use these tools — and what you had to fix, override, or rethink — is part of the evaluation.

Time budget: ~3 hours.

The Agent

Build a conversational agent that can answer questions about Weave docs. It must:

  • Use a tool-calling agent loop — the agent should decide at each step whether to search the docs, read a specific page, run a code snippet, or respond to the user. A single retrieval step followed by generation is not sufficient.
  • Support multi-turn conversation — manage context across turns, not just single-shot Q&A.
  • Self-verify — before responding, the agent should check its answer against the source material to reduce hallucinations.

You choose the LLM, the framework (or no framework), the retrieval strategy, and the tool set.

UX

You are free to design the UX of your choice: web UI, terminal, etc.

Weave Tracing (required)

All agent behavior must be traced using Weave’s new agent tracing data model.

Weave Signals (required)

Set up online monitoring using Weave Signals.

Weave Evaluation (required)

Build an evaluation suite using weave.Evaluation:

  • Create a dataset of at least 10 questions of varying difficulty. Include questions that are multi-hop (require info from multiple pages), ambiguous, or likely to trigger hallucinations.
  • Implement an LLM-as-a-Judge scorer to evaluate the quality of the agent's response based on criteria that you will design.
  • Run the evaluation and include the results in your submission.

What to Submit

A public GitHub repository containing:

  • Source code
  • A README.md with setup instructions, architecture overview, and a summary of your evaluation results
  • A link to your public Weave project

During the interview

We expect the product to be runnable on your own computer during the interview. You will share your screen and demonstrate the agent.

You will also be asked to walk the interviewer through the agent's code base and explain the various components.

What We're Evaluating

This is not a "does the chatbot work" test. We're evaluating your ability to:

  • Make and justify architectural decisions. Why this LLM? Why this retrieval approach? What would you change with more time?
  • Understand the code you ship. You may use AI tools to generate code, but you must be able to explain every component, its role in the system, and its tradeoffs. If something is over-engineered or fragile, we expect you to know that.
  • Design meaningful evaluations. Your dataset and scorers should reveal real failure modes, not just confirm the happy path.
  • Use Weave effectively. Traces should be clear and useful. Evaluations should produce actionable signals.
  • Communicate clearly. Your README, code organization, and commit history should tell the story of how you built this.

If you run into issues with Weave setup, document what happened and how you worked around it. That's useful signal too.

05

Small enough to understand. Real enough to inspect.

The architecture follows the user's journey. Python controls the boundaries; the model chooses the research steps inside them.

01 · Streamlit / app.py

A conversation on your laptop

Streamlit gives us a small web interface without building a separate frontend service. It shows progress, sources, and checks. The tradeoff is limited visual customization.

02 · Sonnet 5.5 / agent.py

A researcher with a limited toolbox

Claude can search, read, execute a small Python example, and submit a draft. A direct loop keeps the choices explainable. Step and repair limits prevent endless research.

03 · BM25 / corpus.py

351 pages, kept locally

BM25 ranks keyword matches. It is fast and useful for exact API names. Saved content fingerprints make experiments repeatable. Semantic paraphrases are a known weakness.

04 · Separate verifier / agent.py

An evidence check before release

A separate model call compares the draft with retrieved passages. Unsupported claims go back for repair. It is designed to catch unsupported claims; it can still miss an error. Its measured effect needs a controlled comparison.

05 · Weave agent tracing / llm.py

A record of what actually happened

Conversation → turn → model and tool spans. Inspect inputs, outputs, usage, source checks, and failures. This exposes decisions and tool activity, not hidden reasoning.

06 · Evaluation + Signals

Two different feedback loops

Opus 5.5 grades a fixed dataset during development. A separate online Signal flags review needs after live turns. Both are fallible; each has a specific, testable job.

Execution has a clear limit: snippets run in a locked-down, offline Python container. We can check small Python logic. We cannot claim that a Weave SDK integration works merely because a standard-library snippet ran.

How the three-hour budget should shape our choices

A planning allocation, not a claim about elapsed time: 20 minutes on the brief and setup, 45 on the agent and retrieval, 25 on the interface and tracing, 40 on evaluation and Signals, 25 on integration checks and packaging, and 25 on documentation and rehearsal. The current build is already underway; this does not restart the clock.

Defer accounts inside the app, vector infrastructure, long-term memory, broad integrations, and elaborate visual effects. The strongest demonstration is a useful task, visible evidence, one instructive failure, and code you understand.
